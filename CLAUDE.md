# Recipe App — Claude Code Guide

## Project Overview

**Trusted Recipe Finder** is a single-page web app that lets users search recipes from their own trusted recipe websites using ingredients they have at home. It requires no AI API keys — all matching is done locally in the browser.

The app is a Vite 8 + React 18 + TypeScript (strict) SPA. The frontend lives in `trusted-recipe-finder/`. It ships with a curated set of built-in recipe sources (pre-indexed weekly by a GitHub Action) and also lets users add their own recipe websites, which are indexed live via a backend function.

Today the app runs on Vercel (frontend + serverless functions, same-origin). A Cloudflare Worker + GitHub Pages deploy path has been added alongside it (see "Deployment" below) but is not yet the default — Vercel remains fully intact until that path is verified end-to-end.

## How It Works

1. **Built-in sources** — On load, the app fetches `data/manifest.json` (served as a static asset) and imports/refreshes any built-in sources whose data is newer than what's already stored, pulling the corresponding `data/<id>.json` file of pre-enriched recipe records straight into IndexedDB. This manifest + per-source JSON is generated by `scripts/build-index.mjs`, run weekly by the `refresh-index` GitHub Action (see `.github/workflows/refresh-index.yml`), so no live scraping is needed for these sources.
2. **Custom sources** — The user can also add their own recipe websites. The app indexes the site via a backend function (`api/scrape.js` on Vercel, or the equivalent route in `worker/index.js` on Cloudflare), which returns a list of recipe URLs and titles.
3. **Enrichment** — The user clicks "Enrich now" for a custom source. The app fetches each recipe page (`api/fetch-recipe.js` / the Worker's equivalent route) and extracts structured data: ingredients, cooking time, instruction count, meal type, cuisine, servings, and image, precomputing ingredient tokens for search. This is stored in IndexedDB (via the `recipes` object store, keyed by source).
4. **Search** — The user enters ingredients one at a time, toggling each as Required or Optional. The local search engine (`src/lib/search.ts`) scores every enriched recipe (built-in and custom) by how many of its ingredients the user has available (entered ingredients + store cupboard), using the precomputed tokens — no re-tokenising on every search. Required ingredients must appear in the recipe; optional ones contribute to the score. A match-threshold slider controls the minimum score shown (default 25%).
5. **Filtering & sorting** — Results are displayed in a virtualised, sortable table (card layout on narrow viewports) with multi-select dropdown filters (meal type, cuisine, time, steps) that filter without re-running the search. Recipes can be starred as favourites, with a dedicated favourites-only view.
6. **Theme** — Dark/light theme follows the OS `prefers-color-scheme` by default, with a manual toggle in the header that persists the user's choice to `localStorage`.

## Key Files

```
trusted-recipe-finder/
  src/
    App.tsx                    # Root — source/search/cupboard/theme state + orchestration
    lib/
      types.ts                 # All shared TypeScript types

      api.ts                   # Backend calls (indexSource, fetchRecipe) + built-in data fetch (fetchManifest, fetchBuiltinSource)

      hooks.ts                 # Shared React hooks (e.g. windowed/virtualised list range)

      styles.ts                # Semantic ThemeTokens + shared style helpers (light/dark)
      constants.ts              # DEFAULT_CUPBOARD, TABS, DEFAULT_MATCH_THRESHOLD
      ThemeContext.tsx         # Theme provider — OS detection, manual toggle, localStorage persistence
    components/
      SearchTab.tsx            # Ingredient entry UI, results table, column filters, sorting
      SourcesTab.tsx           # Add/index/enrich/remove sources (built-in + custom)
      CupboardTab.tsx          # Edit the store-cupboard ingredient list
      FilterDropdown.tsx       # Reusable multi-select dropdown with keyword search
      IngredientEntryBox.tsx   # Chip-based ingredient entry with autocomplete
      ResultRow.tsx            # One result row (table row / card), expands to RecipeCard
      RecipeCard.tsx           # Expanded recipe detail (ingredients, link, image, shopping list)
      Header.tsx               # Tab navigation + theme toggle
  shared/                       # Plain ESM, used by both the frontend and Node build scripts
    scrape-lib.js               # Sitemap indexing + schema.org/Recipe extraction
    tokens.js                   # Ingredient tokenising for search
    recipe-meta.js              # Meal-type/cuisine/time derivation
  scripts/
    build-index.mjs             # Crawls data/sources.json, writes data/manifest.json + data/<id>.json
    copy-data.mjs                # Copies data/ into public/data/ before dev/build
  api/                          # Vercel serverless functions (current default deployment)
    scrape.js                    # Crawls a site for recipe URLs
    fetch-recipe.js              # Fetches and parses a single recipe page
  worker/                       # Cloudflare Worker (additive alternative backend, not yet default)
    index.js                     # Same routes as api/, over the shared scrape-lib, CORS-locked to the Pages origin
    wrangler.toml                 # Worker config, incl. ALLOWED_ORIGIN
```

## Running Locally

```bash
cd trusted-recipe-finder
npm install

# Frontend only (no API calls; built-in sources still load from public/data)
npm run dev

# Frontend + Vercel serverless functions (today's default backend)
npm run dev:all

# Frontend + Cloudflare Worker backend (additive alternative, requires wrangler)
npm run dev:worker
```

Typecheck: `npm run typecheck`
Build: `npm run build`
Deploy (Vercel): `npm run deploy`
Rebuild the built-in recipe index locally: `npm run build-index` (or `npm run build-index -- --source <id>` for one source)

## Deployment

- **Vercel (current default)** — `vercel.json` configures the build; `api/*.js` runs as serverless functions. `npm run deploy` pushes to production.
- **Cloudflare Worker + GitHub Pages (additive, not yet cut over)** — `worker/index.js` serves the same `/api/scrape` and `/api/fetch-recipe` routes as the Vercel functions, restricted by CORS to the `ALLOWED_ORIGIN` configured in `worker/wrangler.toml`. `.github/workflows/deploy-pages.yml` builds the frontend with `VITE_API_BASE` set to the deployed Worker's URL and publishes `dist/` to GitHub Pages on every push to `main`. Cutting over (deleting `api/`, `vercel.json`, and the `vercel` devDependency) is gated on verifying the deployed Pages site end-to-end, which needs a Cloudflare account, `wrangler login`, and the GitHub Pages source set to "GitHub Actions" — steps only the repo owner can do.
- **Weekly data refresh** — `.github/workflows/refresh-index.yml` runs `scripts/build-index.mjs` every Monday and commits any changed files under `data/`.

## Git Workflow

- **Every change request gets its own branch** with the prefix `claude_` (e.g. `claude_multi-select-filters`).
- **The branch description must include the user's original prompt** that instigated the branch, verbatim. Set it with: `git branch --edit-description`
- **Commits are small and regular** — commit after each logical unit of work, not just at the end of a request.
- **No need to ask before committing** — commit freely as work progresses.
- **After completing a request**, assess whether the branch is ready to merge into `main`. If the work is complete and the build passes, merge and push without waiting to be asked.

## Model Selection

Before starting any task, briefly analyse the steps and recommend whether the current model is appropriate or a cheaper one would do equally well:

- **Haiku 4.5** — simple lookups, trivial edits, text formatting, short Q&A
- **Sonnet 4.6** — most coding tasks, multi-step reasoning, feature work, refactors
- **Opus 4.7** — complex architecture, hard reasoning, large cross-file refactors

After giving the recommendation, **stop and wait for the user to confirm** before proceeding. Do not continue with the task until the user explicitly says to.

## Code Style

- Inline styles throughout (no CSS files, no Tailwind) — keeps components self-contained.
- No comments unless the *why* is non-obvious.
- No error handling for impossible cases — trust TypeScript and framework guarantees.
- Validate only at system boundaries (user input, backend API responses).
- Prefer editing existing files over creating new ones.
